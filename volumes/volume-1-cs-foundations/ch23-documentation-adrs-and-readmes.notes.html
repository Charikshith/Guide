Chapter 23 — Documentation, ADRs & READMEs

Concept

Markdown, API docs, docstrings, Architecture Decision Records, and READMEs that actually help.

In one sentence: code shows what and how; documentation must capture why, how to start, and what we decided and what it cost us — in the smallest form that a reader will actually read.

Mental model — signs in a building

The README is the lobby sign: what this place is and how to get in. Docstrings are room labels: what happens in this room. ADRs are the architect's notebook: why the stairs are here and not there. Without the notebook, the next architect tears down a load-bearing wall.

README skeleton

  1. 1. One-sentence description + a status badge.
  2. 2. Quick start: install → run → see a result, in under 10 commands.
  3. 3. Usage examples.
  4. 4. Configuration.
  5. 5. Development: tests, lint, project layout.
  6. 6. Links: docs, ADRs, contributing, license.

Docstring content

Summary line; parameters with types and meaning; return value; raised errors; a runnable example (Python doctest, Rust doc tests compile and run!).

Exam tip!
Never edit an accepted ADR. Write a new one that supersedes it.

ADRs

Short (one page), numbered, immutable once accepted. If the decision changes, write a new ADR that supersedes the old one; don't edit history.

    """Move money between two accounts atomically.

    Args:
        src: Account to debit. Must belong to the caller.
        dst: Account to credit.
        amount_cents: Positive amount in minor units (cents).

        A Receipt with the transaction ID and new balances.

        >>> r = transfer(alice, bob, 500)
        >>> r.src_balance
        9500
    """

Exercises

  1. 1. Write a docstring that a tool can render.
    Solution Use one consistent style (Google, NumPy, or reST) so Sphinx/mkdocstrings can parse the sections. Include a doctest example and run python -m doctest or pytest --doctest-modules in CI so the example stays correct.
  2. 2. Write an ADR for a real past decision.
    Solution Pick something like "why we chose FastAPI" or "why a monorepo". Fill in Context, Options (at least two real alternatives), Decision, and Consequences — include the negatives and a trigger for revisiting. Keep it to one page.
  3. 3. A README says "Run the app". What's missing?
    Solution Prerequisites and versions, the exact commands, required environment variables or config, the expected output (URL, port), and what to do when it fails. A newcomer should succeed by copy-pasting.

Mini project

Generate API docs from docstrings and write a project README + first ADR.

Steps

  1. 1. Add docstrings to every public function of a small project.
  2. 2. Set up mkdocs with mkdocs-material and mkdocstrings; the API page is generated.
  3. 3. Write the README; test the quickstart on a clean machine or container.
  4. 4. ADR 0001 "Record architecture decisions" (the conventional first ADR), plus ADR 0002 for a real choice.
  5. 5. CI runs mkdocs build --strict (fails on broken links) and the doctests.
Done when: a stranger can go from clone to running app using only the README, and the docs build fails if an example breaks.

Open source

  • rust-lang/rust rustdoc — every example in the std docs is compiled and run as a test. Read any page in doc.rust-lang.org/std for the gold standard.
  • mkdocs/mkdocs — Markdown to a static site; see also joelparkerhenderson/architecture-decision-record for ADR templates.

Interview

  1. 1. "What belongs in a docstring vs a README?"
    Answer A docstring documents one unit's contract for its callers: purpose, parameters, return value, errors, example. A README orients a newcomer to the whole project: what it is, how to install, run, and test it, and where to go next. Neither should duplicate the other.
  2. 2. "Why record ADRs?"
    Answer Code shows what was built, not why, or what was rejected. ADRs preserve the context and trade-offs so future engineers don't reverse good decisions by accident or repeat old debates. They make onboarding and reviews faster and are cheap: one page per significant decision.

Checklist

  • document why, not just what
  • write renderable docstrings
  • keep a decision log
