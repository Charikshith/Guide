Chapter 57 — CI/CD & GitHub Actions

Concept

Automating build/test/deploy pipelines with GitHub Actions and deployment gates.

In one sentence: continuous integration automatically builds and tests every change so the main branch is always working, continuous delivery keeps every passing build ready to release, and continuous deployment releases it automatically — with GitHub Actions as a common place to write those pipelines.

Mental model — an airport security line

Every bag (commit) goes through the same scanners (lint, test, build) before it can board. Nobody gets a personal exemption. Delivery is the plane being ready at the gate; deployment is the plane actually taking off — sometimes only after a pilot's final check (a manual approval gate).

CI vs CD vs CD

TechniqueEffect
Cache dependencies (actions/setup-python with cache: pip, setup-uv, setup-node with cache: npm)minutes → seconds

Parallel jobs and test shardingwall time ÷ N
Path filters (paths:)skip unrelated work in monorepos
concurrency: with cancel-in-progressstop outdated runs on the same branch

Example

yaml 
# .github/workflows/ci-cd.yml
name: ci-cd
on:
  push: { branches: [main] }
  pull_request:

permissions:
  contents: read

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
        with: { enable-cache: true }
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run ruff format --check . && uv run mypy src

  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { python: ["3.11", "3.12"] }
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: test }
        ports: ["5432:5432"]
        options: --health-cmd pg_isready --health-interval 5s --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
        with: { enable-cache: true, python-version: "${{ matrix.python }}" }
      - run: uv sync --frozen
      - run: uv run pytest -q --cov=src
        env: { DATABASE_URL: "postgresql://postgres:test@localhost:5432/postgres" }

  build:
    needs: [lint, test]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    outputs: { image: "${{ steps.meta.outputs.image }}" }
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}" }
      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
      - id: meta
        run: echo "image=ghcr.io/${{ github.repository }}:${{ github.sha }}" >> "$GITHUB_OUTPUT"

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - run: ./scripts/deploy.sh staging "${{ needs.build.outputs.image }}"

  deploy-prod:
    needs: [build, deploy-staging]
    runs-on: ubuntu-latest
    environment: production          # protection rule: required reviewers → manual gate
    permissions: { id-token: write, contents: read }   # OIDC to the cloud, no stored keys
    steps:
      - run: ./scripts/deploy.sh production "${{ needs.build.outputs.image }}"

Exercises

  1. 1. Write a CI workflow with build + test + lint.
    Solution The lint and test jobs above: triggered on pull_request, least-privilege permissions, cached dependencies, a matrix across versions, and a service container for the database. Make them required status checks in branch protection so a PR can't merge while red.
  2. 2. Add a manual approval + deploy job.
    Solution Create a production environment in repository settings with required reviewers (and optionally a wait timer and a main-only branch rule). A job with environment: production pauses until approved; its secrets are only available after approval. Deploy the exact image digest built earlier, never a rebuild.
  3. 3. Your CI takes 25 minutes. List five changes to cut it below 5.
    Solution (1) Cache dependencies and Docker layers. (2) Split lint, unit, and integration tests into parallel jobs and shard slow suites. (3) Path filters so docs-only changes skip tests. (4) Cancel superseded runs with concurrency. (5) Profile the slowest tests: replace sleeps with fakes, share expensive fixtures, move slow E2E tests to a nightly job. Also use bigger runners for CPU-bound builds.

Mini project

A full CI/CD pipeline for a service, deployed on every merge.

Steps

  1. 1. Use the service from an earlier chapter (e.g. the Ch 26 to-do API).
  2. 2. PR workflow: lint, types, tests with a coverage threshold, pip-audit/osv-scanner, and gitleaks.
  3. 3. Branch protection: required checks plus a review.
  4. 4. On merge: build the image once, tag it with the SHA, deploy to staging, and run smoke tests.
  5. 5. A production environment with an approval gate; the deploy script waits for health and rolls back automatically.
  6. 6. Record a before/after of pipeline duration after adding caching and parallelism.
Done when: a merged PR reaches staging with no human action, reaches production after one approval, and a deliberately broken release rolls back by itself.

Open source

  • actions/runner — the agent that executes jobs (useful for self-hosting); see also actions/cache, actions/checkout, and nektos/act to run workflows locally.

Interview

  1. 1. "CI vs CD?"
    Answer CI is merging small changes often and automatically building and testing each one, so integration problems appear within minutes. Continuous Delivery keeps every passing build releasable, with a push-button deploy. Continuous Deployment removes the button: every passing change goes to production automatically, relying on strong tests, progressive rollout, monitoring, and automatic rollback.
  2. 2. "How do you keep pipelines fast?"
    Answer Cache dependencies and build layers; fail fast with cheap checks first; parallelize jobs and shard tests; skip unaffected work with path filters or build-graph tools; cancel superseded runs; build once and promote the same artifact; move slow suites to nightly runs; and treat the pipeline's duration as a metric you keep watching.

Checklist

  • validate every commit
  • gate deploys
  • cache dependencies
