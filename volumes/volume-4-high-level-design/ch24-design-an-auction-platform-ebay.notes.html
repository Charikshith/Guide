Ch 24 — Design an Auction Platform (eBay)

Volume 4 — High-Level Design · Contents · ← Chapter 23 — Design a Collaborative Document Editor (Google Docs)

Concept

Not listing, not search. The hard parts: simultaneous bids, the last-seconds rush, fairness about time, telling watchers.

In one sentence: send each bid through one place that orders bids per auction, apply simple deterministic rules (minimum increment, proxy maximum, tie-break, optional soft close), store every decision, close the auction exactly once.

Mental model — a clerk at the auction door

Everyone shouts at once; one clerk writes bids in the book, one at a time. The clerk's order is the order that counts. We build that clerk: correct, fast on a busy item, and safe if it faints.

Scope: timed, ascending auction with proxy bidding. Not: live floor, sealed-bid, Dutch, search, shipping, payment-provider details.

2 · Proxy bidding rules

Bidder gives their maximum. System bids in small steps, only as high as needed to stay in front (eBay help: bids in increments on your behalf, only up to your limit).

Current priceIncrement
$0.01 – $0.99$0.05
$1.00 – $4.99$0.25
$5.00 – $24.99$0.50
$25.00 – $99.99$1.00
$100.00 – $249.99$2.50
$250.00 – $499.99$5.00
$500.00 – $999.99$10.00
$1,000.00 – $2,499.99$25.00
$2,500.00 – $4,999.99$50.00
$5,000.00 and up$100.00

Visible price = one increment above the second-highest maximum, capped at the leader's maximum. Example: $12.00 max outbid by $15.00 max → price $12.50; the $15.00 stays secret.

Rules our engine uses:

  1. New bid ≥ visible price + one increment (first bid ≥ start price).
  2. Bid above leader's max → new leader at (old max + increment), capped at new max.
  3. Bid equal to leader's max → earlier bid wins.
  4. Bid below leader's max → leader stays; price = challenger's max + increment (never above leader's max).
  5. Leader raises own max → price unchanged, closing time unchanged.
  6. Leader's maximum is a secret — never sent to clients.
  7. Same bidder + same bidId again → duplicate, not applied twice.

Rules 3, 5 and the extension rules are design choices, not claims about any site's exact behaviour.

3 · Soft close vs sniping

  • Sniper: bids in the last seconds so nobody can react.
  • Soft close: a bid inside the trigger window pushes the end out by an extension, up to a max number of extensions.
  • Reset mode (ours): new end = bid time + extension, only if later. (Other products add to the current end.)
  • Count an extension only if it moves the end (found by review: an early bid used up the allowance for nothing).
  • A leader who only raises their max does not extend — else they could hold the auction open for free.
  • Cost: end times become unpredictable → payment, packing must wait until extensions stop.

4 · The core problem: two bids at once

Ann bids 50, Bob bids 90; both read "leader Cat". Each computes and blindly writes → last writer wins, even Ann's lower bid. Bob's bid is silently lost (lost update). Need one serialization point per auction.

OptionHowWatch for
Conditional updateread row + version → compute → UPDATE … WHERE version = old → retryretry storms on a hot auction
Redis Lua scriptwhole read-compute-write is one atomic script (server blocked while it runs)keep scripts short; pass every key as an argument; script cache is volatile (reload); durability = Redis persistence + replication
Single writer / auctionpartition by auction ID, one consumer applies in orderhot-partition limits; exactly one writer on failover
Distributed locklock, read, write, releasetimeouts + clocks recreate the double-writer bug

Practical: route all bids for an auction to one owner; apply with a pure function; write state + bid record in one transaction; publish. Conditional update for quiet auctions, single-writer queue for hot ones.

5 · Time, order, fairness

  • Server's clock decides. Stamp on arrival; compare with end time on the same clock.
  • Read the clock again on every retry — a bid that loses a race and retries after the end must be refused.
  • Arrival order = the owner's queue order, not client data.
  • Owner rejects bids after the end; the close job may run late, harmlessly.
  • Latency is unfair by nature — say so; show a server-time countdown.

6 · Closing exactly once

  • Scheduler holds (end time, auction ID): sorted set / delayed queue / timer wheel / durable timers.
  • When due: read state. If an extension moved the end → put back with the new end. Don't close.
  • Close = idempotent conditional update: SET closed = true WHERE closed = false AND end_at <= now.
  • Closing storms (top of the hour): spread over partitions/workers; one durable event per closed auction.
  • After close: outbox → won event → payment saga. Winner doesn't pay → next bidder or relist.

7 · Watchers, fan-out, last minute

  • 100,000 watchers: don't send every bid. Coalesce to 1–2 updates/s/auction, latest only.
  • WebSocket / SSE fed by a pub/sub channel per auction; non-bidders can poll a cached price.
  • Static data (title, photos, price) from CDN / cache. Only the bid endpoint touches the owner.
  • Alerts (outbid, ending soon, won) via a queue — slow email can't slow bidding.
  • Rate-limit bids per user and per auction (bots, loops).

8 · Data model

  • auctions: id, seller, title, start_price, end_at, state, version, leader_id, top_max (secret), price, ext_used, soft-close settings.
  • bids (append-only): auction_id, seq, bid_id (unique), bidder_id, max_amount, outcome, received_at. Keep rejected ones — evidence in disputes. (Demo keeps only their IDs.)
  • watchers, notifications, later orders + payments.
  • Money = integers (cents). Never return top_max from any API: return price, bid count, "you lead?".

9 · Abuse + trust

  • Shill bidding: account linking, device/payment signals, bid patterns; sellers can't bid on own items.
  • Bots / snipers: rate limits, bot detection, soft close; decide on third-party snipers.
  • Retractions / non-payers: retract rules, buyer history, verified payment for high value.
  • AuthN/Z from Ch 19; separate seller and buyer tools.

10 · Estimates (assumptions!)

  • 10M live auctions; 2M bids/hour → ~550 bids/s. Peak 20× → ~11,000/s.
  • Hottest auction: 500 bids/s in its last 10 s → a single-key problem → one owner; CAS retries pile up.
  • Auction state ~1 KB × 10M ≈ 10 GB (fits in memory on a few owners).
  • Bids: 200 B × 48M/day ≈ 10 GB/day (before indexes, replicas).
  • 100k watchers × 1 update/s = 100k msgs/s on one auction → fan-out tier, not the owner.

"""Timed auction with proxy ("maximum") bidding, optional soft close, duplicate-safe bids,
optimistic concurrency, and a closing scheduler. Money is integer cents; time is seconds."""
import heapq
import threading
from dataclasses import dataclass, replace

# eBay's published increment table: from this price (cents) up, the increment (cents) is ...
INCREMENTS = [(0, 5), (100, 25), (500, 50), (2500, 100), (10000, 250), (25000, 500),
              (50000, 1000), (100000, 2500), (250000, 5000), (500000, 10000)]


def increment(price):
    step = INCREMENTS[0][1]
    for floor, s in INCREMENTS:
        if price >= floor:
            step = s
    return step


@dataclass(frozen=True)
class Auction:
    start: int                      # starting price
    end: int                        # closing time
    window: int = 0                 # soft close: a bid this close to the end ...
    extend: int = 0                 # ... moves the end to (bid time + extend), if that is later ...
    max_ext: int = 0                # ... at most this many times
    ext_used: int = 0
    leader: str = None
    top: int = 0                    # the leader's secret maximum
    price: int = 0                  # the price everyone sees
    bids: tuple = ()                # accepted bids: (bid_id, bidder, max, time)
    seen: frozenset = frozenset()   # every (bidder, bid_id) already handled (accepted or rejected)
    closed: bool = False
    version: int = 0                # bumped on every change; used for compare-and-set


def place_bid(a, bidder, mx, now, bid_id):
    """Pure function: (auction, bid) -> (new auction, status). `now` must come from the server's clock."""
    key = (bidder, bid_id)
    if key in a.seen:
        return a, "duplicate"                              # a retry of a request already handled
    if a.closed or now >= a.end:
        return a, "closed"
    seen = a.seen | {key}
    if a.leader is None:
        if mx < a.start:
            return replace(a, seen=seen, version=a.version + 1), "too_low"
        leader, top, price = bidder, mx, a.start
    elif bidder == a.leader:                               # the leader raises their own maximum
        if mx <= a.top:
            return replace(a, seen=seen, version=a.version + 1), "too_low"
        leader, top, price = bidder, mx, a.price
    elif mx < a.price + increment(a.price):                # must beat the visible price by one increment
        return replace(a, seen=seen, version=a.version + 1), "too_low"
    elif mx > a.top:                                       # new leader pays one increment over the old maximum
        leader, top, price = bidder, mx, max(a.price, min(mx, a.top + increment(a.top)))
    elif mx == a.top:                                      # tie: the earlier bid keeps the lead
        leader, top, price = a.leader, a.top, a.top
    else:                                                  # leader stays; price rises toward the challenger's maximum
        leader, top, price = a.leader, a.top, max(a.price, min(a.top, mx + increment(mx)))
    end, used = a.end, a.ext_used
    if (a.extend and bidder != a.leader                   # a leader raising their own maximum never extends
            and now >= a.end - a.window and used < a.max_ext
            and now + a.extend > a.end):                   # only count an extension that really moves the end
        end, used = now + a.extend, used + 1               # soft close ("reset" mode: end = bid time + extend)
    return replace(a, leader=leader, top=top, price=price, end=end, ext_used=used,
                   bids=a.bids + ((bid_id, bidder, mx, now),), seen=seen, version=a.version + 1), "ok"


class Store:
    """Stands in for a database row with a conditional update (compare-and-set on version)."""
    def __init__(self, auction):
        self._a, self._lock = auction, threading.Lock()

    def get(self):
        return self._a

    def cas(self, expected_version, new):
        with self._lock:
            if self._a.version != expected_version:
                return False
            self._a = new
            return True


def bid(store, bidder, mx, now, bid_id, hook=None):
    """`now` is a number (tests) or a function returning the server's clock (production): it is read again
    on every retry, so a bid that loses a race and retries after the end time is correctly refused."""
    while True:                                            # optimistic concurrency: retry on conflict
        a = store.get()
        new, status = place_bid(a, bidder, mx, now() if callable(now) else now, bid_id)
        if hook:
            hook()                                         # tests use this to force an interleaving
        if new is a or store.cas(a.version, new):
            return status


class Scheduler:
    """Closes auctions when due. Extended auctions are re-queued; closing is idempotent."""
    def __init__(self):
        self.heap = []

    def schedule(self, end, auction_id):
        heapq.heappush(self.heap, (end, auction_id))

    def due(self, now, stores):
        closed = []
        while self.heap and self.heap[0][0] <= now:
            _, aid = heapq.heappop(self.heap)
            while True:
                a = stores[aid].get()
                if a.closed:
                    break
                if a.end > now:                            # a late bid pushed the end out: look again later
                    heapq.heappush(self.heap, (a.end, aid))
                    break
                if stores[aid].cas(a.version, replace(a, closed=True, version=a.version + 1)):
                    closed.append(aid)
                    break
        return closed

Exercises

  1. 1. Max $12.00, then max $15.00: what does everyone see; what's secret?
    Solution The $15.00 bidder leads; visible price $12.50 (loser's max + one $0.50 step). The $15.00 max is stored server-side only. The loser just sees they were outbid.
  2. 2. Two bidders read at once and both write back. Why wrong; how do conditional updates fix it?
    Solution Both computed from the same old state; the last writer overwrites, so a higher bid can vanish. With WHERE version = old the second writer is refused, re-reads, recomputes, writes again — both bids applied in some order; the higher survives.
  3. 3. A phone retries the same bid 3 times. Avoid counting it 3 times?
    Solution Client makes one unique bidId and reuses it. Owner records (bidder, bidId) (unique constraint) and doesn't apply a repeat: demo answers duplicate, client reads the auction; production can store and return the original outcome.
  4. 4. One auction gets 500 bids/s and CAS retries pile up. Change?
    Solution Stop racing on the row. Send all bids for it to one owner (partition + single consumer, or a short atomic script) that applies them in order. Keep optimistic updates for quiet auctions.
  5. 5. Phone shows 17:59:58 at tap; server receives at 18:00:00.1; end is 18:00:00. Accepted?
    Solution No. Server's clock decides. Show a server-time countdown and tell users network delay counts against them.
  6. 6. 60 s soft close (reset mode); a challenger bids at 17:59:55 on an 18:00 auction → ends 18:00:55. What does the closer do at 18:00?
    Solution Read state, see the end moved, put the auction back for 18:00:55 — don't close. Closing is a conditional update that checks the end time, so a closer racing a late bid can't close it.

Design

Auction platform, 10M live auctions. Timed ascending, proxy bidding, optional soft close, watchers + alerts, reliable close + payment handoff, abuse protection.

Justify:

  • Owner design: conditional update vs atomic script vs partitioned log; how it changes for hot auctions.
  • Hard vs soft close, and the effect on payment + fulfilment.
  • Server-clock rule; keeping the user's countdown honest.
  • Scheduler: restarts, extensions, closing storms.
  • Watcher coalescing; slow clients.
  • Promise when the owner fails mid-bid (nothing acked is lost; retry is safe).
  • Anti-fraud (shills, bots, verification for high value). Non-paying winner.

Open source

  • redis/redis — atomic Lua scripts, sorted sets for end-time schedules.
  • apache/kafka — partition by auction ID: single-writer ordering + replayable bid log.
  • temporalio/temporal — durable timers + workflows for closing and the payment saga.

How this was checked

  • Increment table: read from eBay's automatic-bidding help page (a reviewer's fetch hit a bot check; secondary sources gave the same tiers). Tests check every boundary.
  • eBay wording "bids in increments on your behalf, only up to your limit": read. "$12 vs $15 → $12.50": reported, not read directly. Visible-price rule and tie-break are design choices.
  • Redis atomic scripts, key arguments, volatile script cache: read from redis.io. Soft-close settings: vendor docs (secondary).
  • Code was run; 11 deliberate bugs each caught. A reviewer found a real bug (extension counted without moving the end), a clock read once across retries, a wrong API example. All fixed + tested.
  • Not a proof for production.

Interview

  1. 1. Two people bid at once; how does the highest win?
    Answer Serialize per auction: conditional update with a version (retry), an atomic script, or a single writer. The bid logic is deterministic so applying bids one at a time in arrival order is consistent. Never blind read-modify-write.
  2. 2. What is proxy bidding; what does the visible price mean?
    Answer Bidder enters a secret maximum; the system bids in increments only as high as needed. Visible price = one increment above the second-highest maximum, capped at the leader's max. The max is never revealed.
  3. 3. Stop last-second sniping?
    Answer Soft close: a bid inside a trigger window extends the deadline, up to a cap. Less useful sniping, but unpredictable end times — payment and fulfilment wait until it truly closes.
  4. 4. Close exactly once?
    Answer Scheduler triggers; close is an idempotent conditional update (closed only if not closed and end time passed). If an extension moved the end, put it back. Won event via an outbox.
  5. 5. 100,000 watchers: live prices?
    Answer Pub/sub per auction → separate WebSocket/SSE fan-out, coalesced to 1–2 updates/s. Static data from caches/CDN. The owner never talks to watchers.
  6. 6. Whose clock decides?
    Answer The server's. Stamp on arrival, compare with the end time, re-read the clock on retries, show a server-time countdown.
  7. 7. A retry after a timeout — what prevents a double bid?
    Answer A client-generated unique bid ID reused on retries, with a unique constraint/seen-set (per bidder). A repeat isn't applied again; answer duplicate or return the stored outcome.
  8. 8. What can go wrong after it ends?
    Answer Winner doesn't pay, payment fails, events delivered twice. Use an outbox for won, a saga for payment with compensation, idempotent consumers, and a fallback: next bidder or relist.

Checklist

  • one serialization point per auction; no blind read-modify-write
  • leader's maximum is secret, never leaves the server
  • unique bid ID per bid, so retries are harmless
  • server clock decides; owner rejects bids after the end
  • closing idempotent, re-checks extensions, publishes via outbox
  • watcher updates coalesced; bids rate-limited
  • money stored as integers
  • test duplicates, races, extensions, crashes
