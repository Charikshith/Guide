Chapter 5 — Proxies, Gateways, Web Servers & Storage Types

Volume 4 — High-Level Design · Contents · ← Chapter 1 — Approaching a System Design Problem · Next → Chapter 13 — Cloud Design Patterns

Concept

Forward vs reverse proxy, API gateway patterns, web vs app servers, CDN push vs pull, block/object/file storage, federation, graph databases.

In one sentence: the boxes between a client and your data — proxies, gateways, web servers, app servers — each have one job, and the boxes at the bottom — block, object, file storage, relational or graph databases — each fit one access pattern, so good design is matching each job and each access pattern to the right box.

Mental model — a hotel. A forward proxy is the guest's personal assistant who makes calls on the guest's behalf. A reverse proxy is the front desk: guests never meet the kitchen, the desk decides who goes where. The API gateway is the concierge with a checklist (ID check, queue management, routing to the right department). Storage is the back office: a locker you rent by the shelf (block), a warehouse where you hand over whole crates and get a ticket (object), and a shared filing cabinet everyone can open (file).

Load balancer vs reverse proxy. Overlap: both accept a client connection and forward it to a backend. A load balancer's core job is spreading traffic across many identical backends (algorithms, health checks, failover) — see Ch 6. A reverse proxy's core job is standing in front of one or more backends and doing work on the way (TLS, caching, compression, rewriting, routing by path or host). In practice nginx, HAProxy and Envoy do both; "load balancer" names the role of spreading load, "reverse proxy" names the position in front of servers. Layer 4 balancers forward TCP without reading HTTP; layer 7 proxies read the request and can route on it.

Web servers vs application servers

Web serverApplication server
Servesstatic files (HTML, CSS, JS, images), plus proxyingdynamic responses: runs your business code
Strengthvery fast at files, many idle connections, TLSruns the language runtime, framework, DB access
Examplesnginx, Apache httpdGunicorn / Uvicorn (Python), Tomcat (Java servlets), Node.js, Puma, Kestrel

The line is blurry: Node and Tomcat also serve files and speak HTTP directly, and nginx can run Lua or call FastCGI. The classic split exists because they scale differently.

Concurrency models

Request flow: client → DNS → CDN (static hits end here) → load balancer / reverse proxy (TLS, routing) → web server (static files, buffers slow clients) → app server (your code) → cache / database. Putting nginx in front of Gunicorn is common because nginx absorbs slow clients while Gunicorn workers stay free for real work.

API gateway

An API gateway is a reverse proxy that understands your API: one entry point for many services.

ResponsibilityWhat it does
Authentication / authorizationvalidate API keys, JWTs, OAuth tokens once, pass identity downstream
Rate limiting & quotasper key or plan (Ch 8)
Routing/orders/* to the orders service, versions, canaries
TLS terminationHTTPS at the edge, plain or mTLS inside
Aggregationcombine several backend calls into one response
Observabilityaccess logs, metrics, tracing headers

Gateway patterns (names from the Azure Architecture Center cloud design patterns and Sam Newman for BFF)

PatternIdeaTrade-off
Gateway Routingone endpoint, route by path, host, header or version to different backendsgateway config grows; a bad route breaks many services
Gateway Offloadingmove shared cross-cutting work (TLS, auth, rate limits, compression, logging) from every service into the gatewayservices must trust the gateway; keep business logic out of it
Gateway Aggregationthe client makes one call; the gateway fans out to N services and merges the resultsfewer client round trips; added latency of the slowest call, partial-failure handling
Backends for Frontend (BFF)one gateway per client type (web, mobile, partner), each shaped for that clientmore services to run; duplicated logic if teams don't share libraries

Trade-offs of any gateway: it is a single point of failure unless run as a redundant fleet behind a load balancer; it adds a hop of latency; and it can become a coupling hotspot — every team needs to change it, and logic creeping in turns it into a distributed monolith's brain. Keep it thin, declarative, and owned by a platform team (or per-team in the BFF style). It differs from a service mesh (Ch 10): the gateway handles north-south traffic (clients to services), the mesh handles east-west (service to service).

CDN push vs pull

Most sites use pull with content-hashed file names (app.3f9a1c.js), which makes invalidation unnecessary.

File system storage vs database storage. A plain file or object store gives you bytes by name. A database adds indexes (find rows without scanning), queries (filter, join, aggregate), transactions (atomic multi-row updates, isolation), constraints, and concurrent-write safety. Plain files or objects win when data is large, opaque and read whole (a photo, a video, a PDF, a log archive), when you only look up by key, and when cost per GB matters. The usual pattern: bytes in object storage, metadata and the key in a database.

Database federation

Federation (functional partitioning) splits databases by function: a users DB, a products DB, an orders DB, each on its own server. Sharding (Ch 11) instead splits one table's rows across servers by a key.

FederationSharding
Split byfeature / bounded contextrow key (user id, hash)
Benefitless read/write load per server, smaller working sets, per-domain scaling and ownershipscales one huge dataset horizontally
Costcross-DB joins become application code or API calls; transactions across DBs need sagas or two-phase commitresharding, hot shards, cross-shard queries
Whenclear domain boundaries; first step toward microservicesone domain's data outgrows one machine

Federation does not remove the single-writer limit inside one function: a busy orders DB may still need replicas or sharding later.

Graph databases

A graph database stores nodes and relationships as first-class data. In the property graph model, nodes and relationships carry labels/types and key-value properties. Relationships are stored as direct pointers, so traversing "friends of friends" follows links instead of computing a join.

FitsExamples
deep relationship traversalssocial networks, org charts
recommendations"people who bought X also bought Y"
fraud and riskrings of accounts sharing devices or cards
network and dependency analysis, knowledge graphsIT topology, permissions graphs

Versus relational: a relational query needs one self-join per hop, and cost grows with hops and table size; a graph traversal cost grows with the part of the graph visited. If your queries are mostly filters, aggregates and fixed-depth lookups, a relational database is the better default. Examples: Neo4j (query language Cypher), Amazon Neptune, JanusGraph, ArangoDB; PostgreSQL can also do recursive queries.

Denormalization and SQL tuning

Denormalizing (duplicating data to avoid joins) and tuning queries (indexes, EXPLAIN, avoiding N+1) are covered in Vol 1 Ch 46 and, at scale (replicas, partitioning, caching), in Ch 11. Rule of thumb: normalize first, tune the slow queries, denormalize only for measured read hot spots and own the cost of keeping copies in sync.

Example

nginx 
# nginx as TLS-terminating reverse proxy + web server in front of a Gunicorn app
upstream app {
    server 127.0.0.1:8000;          # gunicorn
    server 127.0.0.1:8001;
    keepalive 32;
}

server {
    listen 443 ssl;
    server_name shop.example.com;
    ssl_certificate     /etc/ssl/shop.crt;
    ssl_certificate_key /etc/ssl/shop.key;

    location /static/ {             # web server job: files straight from disk
        root /var/www;
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    location /api/ {                # reverse proxy job: pass to the app server
        proxy_pass http://app;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
bash 
# app server: pre-forked worker processes (2 x cores + 1 is a common starting point)
gunicorn app:app --workers 5 --bind 127.0.0.1:8000
python 
# Gateway aggregation: one client call, three backend calls in parallel
import asyncio, httpx

async def home(user_id: str) -> dict:
    async with httpx.AsyncClient(timeout=0.5) as c:
        u, o, p = await asyncio.gather(
            c.get(f"http://users/users/{user_id}"),
            c.get(f"http://orders/orders?user={user_id}&limit=3"),
            c.get("http://products/featured"),
            return_exceptions=True,          # partial failure: do not fail the whole page
        )
    return {
        "user": u.json() if not isinstance(u, Exception) else None,
        "orders": o.json() if not isinstance(o, Exception) else [],
        "featured": p.json() if not isinstance(p, Exception) else [],
    }
cypher 
// Property graph: friends-of-friends recommendation (Cypher)
MATCH (me:User {id: 42})-[:FOLLOWS]->(:User)-[:FOLLOWS]->(rec:User)
WHERE rec <> me AND NOT (me)-[:FOLLOWS]->(rec)
RETURN rec.name, count(*) AS mutual
ORDER BY mutual DESC
LIMIT 10;
sql 
-- the same two-hop query in SQL needs a self-join per hop
SELECT f2.followee_id, COUNT(*) AS mutual
FROM follows f1
JOIN follows f2 ON f2.follower_id = f1.followee_id
WHERE f1.follower_id = 42
  AND f2.followee_id <> 42
  AND f2.followee_id NOT IN (SELECT followee_id FROM follows WHERE follower_id = 42)
GROUP BY f2.followee_id
ORDER BY mutual DESC
LIMIT 10;

Exercises

  1. 1. Explain the difference between a forward proxy and a reverse proxy, and name one real product for each.
    Solution A forward proxy acts for clients (Squid on a corporate network filters and caches outbound traffic, hiding client IPs). A reverse proxy acts for servers (nginx, HAProxy or Envoy in front of a service handles TLS, caching and routing, hiding the backends). The question to ask: whose side is the proxy on, and who knows it is there?
  1. 2. Pick block, object or file storage for: a PostgreSQL data volume, user-uploaded profile photos, a shared folder mounted by 10 web servers.
    Solution PostgreSQL: block (EBS) for low-latency random I/O. Profile photos: object (S3), with the key stored in the database and a CDN in front. Shared folder: file storage (EFS/NFS), because many machines need a POSIX file system at once. If the shared folder only holds uploaded assets, consider moving it to object storage instead.
  1. 3. Your single database holds users, products and orders and is CPU-bound. When is federation a better first step than sharding, and what breaks?
    Solution When the load comes from different functions and the domains are mostly independent: split into users, products and orders databases. Joins across them move into application code or an API, and a checkout touching two databases needs a saga or two-phase commit instead of one transaction. If one table (say orders) is itself too big for one machine, sharding is still needed later.
  1. 4. When would you choose a graph database over PostgreSQL?
    Solution When the core queries traverse relationships with unknown or deep depth (fraud rings, recommendations, permission graphs) and join cost grows with every hop. For fixed-depth lookups, filters, aggregates and strong transactional needs, stay relational; recursive CTEs cover occasional graph queries.

Mini project

A tiny edge stack with docker compose: nginx → gateway → services.

Steps

  1. 1. Three small services, each with its own SQLite or Postgres database (federation in miniature).
  2. 2. A FastAPI gateway: API-key check, path routing, and a /home endpoint that aggregates the three services with timeouts and partial failure.
  3. 3. nginx in front: TLS with a self-signed cert, /static/ served from disk, everything else proxied.
  4. 4. Add a second gateway instance and let nginx balance across them; kill one and show requests keep working.
  5. 5. Store uploaded images in MinIO (S3-compatible object storage) and keep only the key in the database.
Done when: /home returns merged data even if one service is down (that field empty), static files never reach the gateway, and killing a gateway instance causes no failed requests.

Design

Design the edge and storage tier of an online shop.

Requirements: 5M users, 20k peak requests/s at the edge (80% static assets and cacheable GETs), web and mobile apps with different payloads, product images up to 5 MB, orders must be transactional, "customers also bought" recommendations.

Capacity: 20k req/s × 20% dynamic = ~4k req/s reach the gateways; across 4 gateway nodes that is ~1k req/s each, comfortable for one proxy node. Images: 1M products × ~5 MB originals = ~5 TB, trivial for object storage and expensive on block storage.

Decisions to justify

  • Pull CDN with hashed file names for assets; product images in object storage behind the CDN, so the origin only sees misses.
  • Redundant BFFs (web and mobile) behind a load balancer: no single point of failure; a shared library (not a shared gateway) for auth and rate limiting to limit duplication.
  • Federation by domain: users, products and orders databases scale and fail independently; orders keeps replicas, and checkout uses a saga rather than a cross-DB transaction.
  • Block storage (EBS-style volumes) only under the databases; object storage for images and exports; file storage not needed.
  • Graph DB only for recommendations, fed asynchronously from order events; the orders DB stays the source of truth.
  • Trade-off acknowledged: more databases mean more operations work and no cross-domain joins; accept it for the isolation.

Interview

  1. 1. "What is the difference between a load balancer and a reverse proxy?"
    Answer They overlap heavily and products like nginx, HAProxy and Envoy do both. A load balancer is defined by spreading traffic across several identical backends with health checks and failover. A reverse proxy is defined by sitting in front of servers and doing work on the way: TLS termination, caching, compression, rewriting, path or host routing. A load balancer may work at layer 4 without reading HTTP; a reverse proxy normally works at layer 7.
  1. 2. "Why put nginx in front of Gunicorn or Tomcat?"
    Answer The event-driven web server handles thousands of slow or idle client connections cheaply, terminates TLS, serves static files directly and buffers requests and responses. The app server's limited worker processes or threads then spend their time running code, not waiting on slow clients.
  1. 3. "Explain the gateway patterns and the risks of an API gateway."
    Answer Routing sends requests to backends by path, host or version. Offloading moves shared concerns (TLS, auth, rate limiting, logging) out of each service. Aggregation fans out and merges calls so clients make one request. BFF gives each client type its own gateway shaped to its needs. Risks: a single point of failure unless redundant, an extra hop of latency, and coupling if business logic accumulates in it. Keep it thin and redundant, and split per client with BFFs when teams or payloads diverge.
  1. 4. "Block, object or file storage for a given workload?"
    Answer Block for databases and boot volumes needing low-latency random I/O from one machine. Object for large, immutable, read-whole data (images, video, backups, logs) at the lowest cost per GB and near-unlimited scale. File when several machines need a shared POSIX file system. Often the best design stores bytes in object storage and the metadata in a database.
  1. 5. "Federation vs sharding?"
    Answer Federation splits databases by function (users, products, orders), reducing load per server and giving domains independent scaling, at the price of cross-database joins and transactions. Sharding splits one dataset's rows by key across servers, scaling a single large domain but adding resharding and cross-shard query complexity. Federate first along domain lines; shard a domain when its own data outgrows one node.

Checklist

  • know whose side each proxy is on
  • keep the gateway thin and redundant
  • pick block, object or file storage by access pattern
  • choose pull or push CDN deliberately
  • federate by domain before sharding
  • use a graph database only for relationship-heavy queries
