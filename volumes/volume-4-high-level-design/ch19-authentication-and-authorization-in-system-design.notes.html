Ch 19 — Authentication & Authorization in System Design

Volume 4 — High-Level Design · Contents · basics first: Vol 2 Ch 12

Concept

Where is identity checked? How does it travel? How is it revoked? What if the IdP dies?

In one sentence: authenticate once at the edge → a signed identity every hop verifies cheaply; authorize in the service that owns the data; keep working when the identity service is down.

Mental model — an airport

Passport once at check-in (IdP). Boarding pass = token. Gates scan it without phoning the airline (local verify). Staff doors need a different badge (service identity). Cancelled pass → list gates sync (revocation). The gate agent — not check-in — decides if you may board this flight (authZ at the resource).

Remember!
Gateway = who + coarse. Service = fine-grained.

3 · Token architecture

  • A · JWT everywhere: IdP issues short JWT; everyone verifies with cached JWKS. Fast, no call. Weak: readable, hard to revoke.
  • B · Opaque outside, JWT inside ("phantom token"): client holds a random token; gateway introspects (cached) and swaps for a short internal JWT. Claims hidden, revocation instant at the edge.
  • C · Token exchange (RFC 8693): A swaps the user's token for one scoped to B → B sees who + via whom; can't be replayed against C. Limits the confused deputy.

Propagating identity:

  • Never trust X-User-Id because it arrived. Gateway strips client copies; accept only over mTLS.
  • Pass a signed token (survives queues, async hops: put user + tenant in the message, re-check).
  • Small claims: IDs + scopes, not whole permission lists.

4 · Service-to-service identity

MechanismNotes
mTLS + workload identityshort-lived cert naming the workload (SPIFFE ID); mesh or SPIRE automates; no shared secrets
OAuth2 Client Credentialsservice's own token; good across trust zones + third parties
Cloud workload identityIAM roles for pods/VMs; no long-lived keys
Static API keyslast resort; rotate, scope, keep out of code

Identity is half. Add allow rules: "only orders may POST /charges on payments". Default deny between services → smaller blast radius (Ch 18).

5 · Keys + rotation

  • IdP signs with a private key (KMS/HSM); everyone else gets only public keys from JWKS.
  • Header has kid. Rotate with overlap: publish new key → sign with it → keep old public key until old tokens expire.
  • Verifiers cache JWKS, refetch on unknown kid (rate-limited!), keep the cache if the IdP is unreachable.
  • Allow ~30–60 s clock skew on exp/nbf; NTP on servers.

6 · Revocation at scale

ApproachDelayCost
Short TTL only (5–15 min)up to TTLnone
Deny-list of jtiseconds1 cache read; entries live until exp
Per-user "valid since" versionseconds1 cache read; 1 write revokes all of a user's tokens
Opaque + introspectionimmediatenetwork call (cache a few s)

Pick by risk: bank = seconds; news site = 15 min. Sensitive actions (password change, money) → fresh login / step-up whatever the token says.

7 · Sessions + the login path

  • Session store: Redis cluster, random session ID, sharded by ID, TTLs. ~10M active × ~0.5 KB ≈ 5 GB (rough estimate).
  • Login is CPU-heavy on purpose: Argon2id/bcrypt = tens of ms. Illustrative: 50 ms → ~20 logins/s/core → 2,000/s ≈ 100 cores. Run hashing in a separate auth service so a spike can't starve the product.
  • Credential stuffing = main threat: rate-limit by IP and account (Ch 8), breached-password check, bot detection, MFA, identical error for "no user" / "wrong password".
  • Passkeys: "guess a password" → "steal a device". MFA required for admin + sensitive actions.

8 · Authorization at scale

PlacementGood forWatch for
Library in each servicelow latency, simpleversion drift
Sidecar PDP (OPA/Cedar)one language, no off-box hoppolicy distribution + testing
Central PDP serviceone place to change rules; relationship graphsextra hop + critical dependency → cache, tight timeouts
  • ReBAC (Zanzibar-style, SpiceDB): walk user → group → folder → doc. Hard part = consistency: a just-revoked permission must not come from a stale cache ("new enemy problem") → consistency token passed with the write.
  • List endpoints: don't fetch 10,000 rows and filter in code. Push the filter into the query (WHERE tenant_id = ?, RLS — Ch 15) or ask the PDP for allowed IDs.
  • Speed: a few ms budget; cache positive decisions briefly; fail closed for writes + sensitive reads.
  • Audit every decision: who, what, resource, allow/deny, policy version.

9 · Multi-tenant + B2B

  • tenant_id in the token, checked against the resource's tenant on every access. Never trust tenant from body/URL alone.
  • Enterprise SSO (bring your own IdP): per-tenant OIDC/SAML config; map user → tenant (email domain or tenant URL); SCIM for joiners/leavers.
  • Roles per tenant: (user, tenant, role) — admin here, viewer there.
  • Support impersonation = separate, audited, time-boxed token. Never a shared admin password.

10 · Third-party + public APIs

  • Developers: OAuth2 clients (Code + PKCE for a user; Client Credentials for their backend) + scopes.
  • API keys: scopes, owner, per-key rate limit (Ch 8), rotation.
  • Webhooks you send: sign body + timestamp with HMAC (receiver rejects replays). Webhooks you receive: verify first.

11 · Availability + failure

  • IdP is on the critical path of login, not of every request.
  • Local JWT verify + cached JWKS → requests flow while IdP is down; only new logins + refreshes fail.
  • Multi-zone IdP (multi-region for big systems); refresh-token grace window; client backoff + jitter (no stampede on recovery).
  • Fail closed, but separate can't decide from denied; alert on spikes of either.
  • Build vs buy: identity is unforgiving → mature product or open-source IdP.

# OPA policy (Rego): scope + same-tenant check. Anything not allowed is denied.
package orders.authz
import rego.v1

default allow := false

scopes := split(input.claims.scope, " ")

allow if {
    input.method == "GET"
    "orders:read" in scopes
    input.claims.tenant_id == input.resource.tenant_id
}

allow if {
    input.method == "POST"
    "orders:write" in scopes
    input.claims.tenant_id == input.resource.tenant_id
    input.claims.role in {"admin", "editor"}
}
python 
# Revocation check at the gateway: deny-list plus per-user "valid since" (Redis).
def is_revoked(claims: dict, redis) -> bool:
    if redis.exists(f"revoked:jti:{claims['jti']}"):              # one token revoked
        return True
    valid_since = redis.get(f"user:{claims['sub']}:valid_since")  # all tokens before this time
    return valid_since is not None and claims["iat"] < int(valid_since)

def revoke_user(redis, user_id: str, now: int):
    redis.set(f"user:{user_id}:valid_since", now)                 # logout everywhere / password change

Exercises

  1. 1. Why must inner services verify identity again if the gateway did?
    Solution Zero trust: the gateway can be bypassed (misrouted call, compromised pod, internal tool), and only the data owner can decide object-level access. A second local verify costs microseconds. Gateway: coarse checks + rate limits. Services: fine ones.
  2. 2. A service reads the user from X-User-Id. What goes wrong? Fix?
    Solution Anything reaching the service can set it and become any user. Accept identity only from a signed token or an mTLS-authenticated gateway; gateway strips client copies; service verifies the signature itself.
  3. 3. Revocation within 10 s, 5M active users, 20,000 req/s. Pick.
    Solution Short access tokens (5–10 min) + per-user "valid since" in replicated Redis. 20,000 reads/s is small for Redis (add a 1–5 s local cache if needed). One write revokes all of a user's tokens. A jti deny-list works but needs an entry per token. Opaque tokens give instant revocation but put introspection on every request.
  4. 4. The IdP is down for 20 minutes. What works, what fails?
    Solution Valid unexpired tokens keep working (local verify, cached JWKS). New logins and refreshes fail; expiring tokens start failing within the token lifetime. Mitigate: cache JWKS, multi-zone IdP, refresh grace window, client backoff + jitter. Security decisions still fail closed.
  5. 5. A customer wants to log in with their own company SSO. What do you build?
    Solution Per-tenant IdP config (OIDC/SAML), tenant lookup at login (domain or URL), map IdP user → tenant membership + role, SCIM for provisioning/deprovisioning, tenant_id in the token checked on every access, and a break-glass admin path for their IdP outage.

Mini project

Gateway + auth service + two services: token exchange, mTLS allow rules, key rotation.

  1. Auth service issues 10-min RS256 JWTs (iss, aud, sub, tenant_id, scope) and serves JWKS.
  2. Gateway verifies locally (cached JWKS), strips client identity headers, checks Redis for revocation.
  3. orders gets an OPA sidecar: scope + same-tenant.
  4. orders calls payments over mTLS with a token exchanged for audience payments; allow only that caller + path.
  5. Rotation: publish a 2nd key, switch signing, serve both until old tokens expire.
  6. Chaos tests: stop auth (existing tokens still work); revoke a user (fails within target); call payments without a cert (refused); tenant-A token on tenant-B resource (denied).
Done when all four chaos tests pass, rotation causes zero failed requests, and every denial is in a decision log with a reason.

Design

1 · Multi-tenant B2B SaaS with enterprise SSO. 5,000 tenants, 2M users; some need SAML/OIDC + SCIM, others email + MFA.

  • Shape: IdP fronts login; per-tenant federation; gateway verifies JWTs; services enforce tenant_id + roles; SCIM endpoint; audit log.
  • Justify: build vs buy IdP · how login finds its tenant · role storage + caching · tenant-IdP outage (break-glass) · per-tenant signing keys? · audited support impersonation.

2 · Public API platform. 50,000 clients, 20,000 req/s peak, user-granted (OAuth2) + server keys, per-client limits + billing, instant disable of an abused key.

  • Shape: portal issues clients/keys; Code + PKCE and Client Credentials; keys stored hashed with prefix, scopes, owner; gateway checks (cached) + per-client rate limits; usage events → queue → billing; HMAC-signed webhooks.
  • Justify: opaque keys + cached lookup vs JWT · how fast a disabled key must stop · rotation without downtime · logging without leaking secrets.

3 · Login + sessions for 100M users. 10M DAU, peak 2,000 logins/s, mobile + web, social sign-in, passkeys, stuffing defence, revoke ≤ 10 s on password change.

  • Shape: autoscaled auth service behind rate limits + bot checks; short access JWT + rotating refresh tokens (HttpOnly cookie on web, secure storage on mobile); Redis for refresh families + user version; passkeys preferred; multi-region.
  • Justify: sessions vs tokens for web · cores for the login path + where hashing runs · IP + account limits without locking out real users · active-active login and avoiding a password change taking effect in only one region.

Open source

  • keycloak/keycloak, ory/hydra — IdPs + OAuth2/OIDC servers.
  • spiffe/spire — workload identity (SPIFFE IDs, short-lived certs).
  • envoyproxy/envoy (jwt_authn, ext authz), oauth2-proxy/oauth2-proxy — OIDC login in front of an app.
  • open-policy-agent/opa, authzed/spicedb — policy engine; Zanzibar-style ReBAC.
  • hashicorp/vault — dynamic credentials, transit/signing engine.

Interview

  1. 1. Where would you authenticate in microservices?
    Answer Edge first: verify the token, rate-limit, coarse scopes. Then each service verifies the signed identity again (local JWT verify or mTLS) and does object-level authZ — the service owns the data and the gateway can be bypassed. The IdP issues tokens; it isn't called per request.
  2. 2. How do services call each other securely?
    Answer Short-lived workload identity (mTLS via mesh/SPIRE, or client-credentials tokens), verified both sides, plus default-deny allow rules per caller and path. For a user, exchange their token for one scoped to the next service.
  3. 3. JWT revocation at scale?
    Answer Short access tokens bound the delay. For faster cut-off keep a per-user "valid since" version (or jti deny-list) in a replicated cache the gateway reads once per request, and revoke refresh tokens. Immediate need → opaque tokens + cached introspection.
  4. 4. Auth service down — what happens?
    Answer Valid tokens keep working (local verify, cached keys). Logins and refreshes fail, so tokens expire into errors within their lifetime. Reduce impact: multi-zone/region IdP, JWKS cache, refresh grace window, client backoff, fail-closed decisions with alerts.
  5. 5. Enterprise SSO for multi-tenant SaaS?
    Answer Per-tenant OIDC/SAML federation, tenant resolution at login, memberships + roles in your DB, SCIM, tenant_id in tokens checked on every access, per-tenant audit logs, break-glass admin.
  6. 6. Central policy service or library per service?
    Answer Library/sidecar: low latency, no new dependency, risk of drift. Central: one place to change rules, relationship graphs, but extra hop + critical dependency → cache + tight timeouts. Common: shared policy language (OPA/Cedar), sidecar evaluation, central distribution.
  7. 7. Protect login from credential stuffing?
    Answer Rate-limit per IP and account, breached-password checks, bot detection/CAPTCHA, MFA or passkeys, identical errors, alert on failure spikes. Hash in its own scalable service so attacks can't starve other traffic.

Checklist

  • authenticate at the edge, verify again inside services
  • never trust identity headers from an unverified source
  • workload identity + default-deny service calls
  • rotate signing keys with overlap; cache JWKS
  • revocation approach matches the risk
  • identity service off the per-request path
  • tenant + object checks in the owning service
  • log every authorization decision
