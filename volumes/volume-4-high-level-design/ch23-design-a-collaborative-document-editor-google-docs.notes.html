Ch 23 — Design a Collaborative Document Editor (Google Docs)

Volume 4 — High-Level Design · Contents · ← Chapter 22 — The 30-System Design Portfolio

Concept

Many people type at once. Each sees their own keys instantly. Everyone must end with the same document.

In one sentence: apply every edit locally at once, send it to a server that fixes one global order, and use OT or a CRDT so concurrent edits applied in different orders still give identical text.

Mental model — two editors, one printed page

Doc "abc". Alice inserts x at the start. Bob deletes c ("delete char 2"). Replay Bob's step unchanged on Alice's copy → deletes the wrong letter. OT rewrites it to "delete char 3". A CRDT gives every letter a permanent name, so "delete the letter named c" never depends on position.

2 · Why the obvious ways fail

  • Lock the document → one at a time; stale locks from closed tabs.
  • Last write wins (whole doc) → second save erases the first person's work.
  • Send whole doc per keystroke → too much data, still needs a merge rule.
  • "insert at position 5" unchanged → positions go stale when another edit lands first.

So: send operations, and make concurrent ops commute (arrival order doesn't change the result).

3 · Operational transformation (OT)

  • Ops like insert(pos, ch), delete(pos). An op made on an old version is transformed past the ops it hasn't seen.
  • Example: "abc"; O1 = insert x at 0; O2 = delete pos 2. After O1, O2 becomes delete 3. Either order → xab.
  • TP1: a then T(b,a) = b then T(a,b), for concurrent a, b.
  • TP2: 3-op condition; needed when ops can be transformed in different states (no central server). Our demo passes TP1, not TP2 (8 of 729 triples fail) → OK only with a central server.
  • History: Ellis & Gibbs 1989 (first algorithm) → Jupiter 1995 (central server) → Wave / Docs (Wikipedia: 2009; Google's blog series on Docs: Sept 2010).
  • Pros: small messages, no per-char IDs, battle-tested.
  • Cons: transform rules explode with rich text; practical systems need a central server; undo is tricky; early algorithms had bugs, proofs are error-prone → test with random runs.
Remember!
OT = fix the instruction.
CRDT = fix the data (IDs).

4 · CRDTs

  • Replicas converge if they get the same updates and concurrent updates commute (Shapiro et al. 2011, "strong eventual consistency"). Op-based designs need causal delivery; state-based designs merge whole states.
  • Sequence CRDT: every char has a unique ID. Insert = "after char ID". Delete = tombstone (keep it so later refs still work). Same-spot inserts → ID order decides, identically everywhere.
  • Pros: no central order needed; offline-first / peer-to-peer.
  • Cons: per-char metadata; tombstones need GC; interleaving pitfalls.
  • Speed is about the implementation. Gentle's benchmark (2021, 260k edits, ~100k chars): Automerge preview 291 s / 880 MB · list CRDT 31 s · Yjs 0.97 s / 3.3 MB · plain splice 0.61 s. One author, one machine, local single-user replay only.

5 · Figma-style: last writer wins per property

  • Server = authority, decides order. One property of one object: last value the server gets wins. Different properties never conflict.
  • Child order by fractional indexing; parent + position stored together (atomic move); server rejects cycles.
  • Figma: inspired by CRDTs but not true CRDTs; skipped OT (too complex for them).
  • Good for design tools / forms. Wrong for text — two people typing in one paragraph must both keep their words.

7 · Architecture

  • Client: applies edit locally, queues unacked ops, talks over WebSocket.
  • One owner server per document (Figma: a process per doc). Route by doc ID; ownership kept in a small shared store so another server can take over.
  • Op log: append every accepted op with a revision number before the ack → durable truth.
  • Snapshots every N revisions → open = snapshot + replay tail.
  • Presence (cursors): ephemeral, pub/sub, never in the log.
  • Metadata (owner, title, ACL, comments): normal SQL DB.
  • Permissions checked at connect and every op (Ch 19). A viewer can't send edits.
  • Comments anchored to a range → transform the anchors with the ops.

8 · One edit's journey (OT)

  1. Alice types. Her client applies it at once, sends (op, base rev) if nothing is in flight.
  2. Server transforms it past newer ops, applies, appends to log, assigns next rev.
  3. Server acks Alice, broadcasts the transformed op to the others.
  4. Others transform it against their own unacked edits, then apply. Alice, on ack, sends her next queued edit (one in flight keeps clients simple).

9 · Scale, failure, edge cases

  • Hot doc (100s of editors): cap active editors, rest read-only; batch 50–200 ms; coalesced stream to viewers.
  • Reconnect: send last rev + unacked ops (or reload and reapply — Figma downloads a fresh copy).
  • Duplicates: op ID (client ID + counter) → retry after a lost ack is ignored.
  • Server crash: new owner = snapshot + log replay; clients resend anything unacked.
  • Never two servers accepting ops for one doc (lease / consensus-backed owner record).
  • Log growth: merge typing runs, snapshot, retention policy.
  • Undo = your own last edit only (inverse op transformed / new CRDT op on same IDs).
  • Big paste = one op, not thousands of single chars.

10 · Estimates (assumptions!)

  • 10M DAU; peak 400k typing at once. ~40 wpm ≈ 3–4 chars/s → at most ~3 non-empty msgs/s; take 2 average (content only, no cursors) → 0.8M in/s.
  • Fan-out 1.5 → 1.2M out/s. In + out ≈ 2M msgs/s.
  • 40k msgs/s per server (assumed) → 50 servers. 1M connections at 20k each → 50. With 2–3× headroom → 100–150.
  • Log: 20 B × 3 chars/s × 400k ≈ 24 MB/s ≈ 2 TB/day only if peak lasted all day. Compaction cuts it ~10× (state your factor).

"""Operational transformation for plain text: single-character insert/delete,
a central server that orders operations (the Jupiter / Google-style design)."""

NOP = ("nop",)


def apply(doc, op):
    if op[0] == "ins":                      # ("ins", pos, char, site)
        return doc[:op[1]] + op[2] + doc[op[1]:]
    if op[0] == "del":                      # ("del", pos)
        return doc[:op[1]] + doc[op[1] + 1:]
    return doc


def transform(a, b):
    """Rewrite op `a` so it still means the same thing after concurrent op `b` has been applied."""
    if a == NOP or b == NOP:
        return a
    if a[0] == "ins" and b[0] == "ins":
        # same position: the lower site id goes first, so both sides pick the same order
        if a[1] < b[1] or (a[1] == b[1] and a[3] < b[3]):
            return a
        return ("ins", a[1] + 1, a[2], a[3])
    if a[0] == "ins" and b[0] == "del":
        return a if a[1] <= b[1] else ("ins", a[1] - 1, a[2], a[3])
    if a[0] == "del" and b[0] == "ins":
        return a if a[1] < b[1] else ("del", a[1] + 1)
    if a[1] < b[1]:                         # del vs del
        return a
    if a[1] > b[1]:
        return ("del", a[1] - 1)
    return NOP                              # both deleted the same character


class Server:
    def __init__(self, doc=""):
        self.doc, self.log = doc, []        # log[i] = the i-th operation, in server order

    def receive(self, op, base_rev):
        """A client built `op` when it had seen `base_rev` operations."""
        for old in self.log[base_rev:]:     # transform past everything the client has not seen
            op = transform(op, old)
        self.doc = apply(self.doc, op)
        self.log.append(op)
        return op                           # broadcast this form to the other clients


class Client:
    def __init__(self, site, doc=""):
        self.site, self.doc, self.rev = site, doc, 0
        self.inflight, self.buffer = None, []   # one op on the wire, the rest queued

    def local(self, op):
        self.doc = apply(self.doc, op)      # show my own edit immediately
        if self.inflight is None:
            self.inflight = op
            return (op, self.rev)           # message to send to the server
        self.buffer.append(op)
        return None

    def on_ack(self):
        self.rev += 1
        self.inflight = None
        if self.buffer:
            self.inflight = self.buffer.pop(0)
            return (self.inflight, self.rev)
        return None

    def on_remote(self, op):
        pending = ([self.inflight] if self.inflight else []) + self.buffer
        mine = []
        for p in pending:                   # pass the remote op through my unacknowledged ops
            op, p = transform(op, p), transform(p, op)
            mine.append(p)
        if self.inflight:
            self.inflight, self.buffer = mine[0], mine[1:]
        else:
            self.buffer = mine
        self.doc = apply(self.doc, op)
        self.rev += 1

"""A tiny sequence CRDT (RGA style): every character has a unique id; inserts name the
character they go after; deletes leave a tombstone. Operations commute, so replicas
converge with no central server (they must still deliver an op after the ops it depends on)."""


class Replica:
    def __init__(self, site):
        self.site, self.clock = site, 0
        self.nodes = [("head", "", False)]          # (id, char, deleted); id = (counter, site)
        self.seen = set()                           # ids of ops already applied (makes delivery idempotent)

    def _index(self, node_id):
        for i, n in enumerate(self.nodes):
            if n[0] == node_id:
                return i
        return None

    def text(self):
        return "".join(c for _, c, dead in self.nodes if not dead)

    def _visible_ids(self):
        return [i for i, _, dead in self.nodes[1:] if not dead]

    def local_insert(self, pos, char):
        ids = self._visible_ids()
        after = ids[pos - 1] if pos > 0 else "head"
        self.clock += 1
        op = ("ins", (self.clock, self.site), after, char)
        self.apply(op)
        return op

    def local_delete(self, pos):
        op = ("del", ("d", self._visible_ids()[pos]))
        self.apply(op)
        return op

    def ready(self, op):                            # have the ops this one depends on arrived?
        target = op[2] if op[0] == "ins" else op[1][1]
        return target == "head" or self._index(target) is not None

    def apply(self, op):
        if op[0] == "ins":
            _, node_id, after, char = op
            if node_id in self.seen:
                return
            self.seen.add(node_id)
            self.clock = max(self.clock, node_id[0])
            i = self._index(after) + 1
            while i < len(self.nodes) and self.nodes[i][0] > node_id:   # skip newer siblings
                i += 1
            self.nodes.insert(i, (node_id, char, False))
        else:
            target = op[1][1]
            i = self._index(target)
            self.nodes[i] = (target, self.nodes[i][1], True)            # tombstone; repeating it is harmless

Exercises

  1. 1. Walk the abc example by hand; what if the delete is not transformed?
    Solution Alice has xabc; Bob has ab. Unchanged del(2) on xabc removes b → xac (wrong). Transformed del(3) removes c → xab; Bob applies ins(0,x) to ab → xab.
  2. 2. Two people insert at the same spot. How do OT and the CRDT order them?
    Solution OT: a fixed tie-break (lower site ID first) used identically on both sides. CRDT: unique ID (counter, site); siblings sorted by ID, same on every replica.
  3. 3. Why keep tombstones?
    Solution Another replica may have inserted "after" that char before seeing the delete. Removing it would leave that reference pointing at nothing. GC removes tombstones only when every replica has seen the delete.
  4. 4. A user is offline an hour. OT / CRDT / Figma-style?
    Solution OT: resend unacked ops with base rev; server transforms past an hour of history (many products reload and reapply). CRDT: exchange missing ops in any order and converge. Figma-style: download a fresh copy, reapply offline edits; conflicting properties → last value the server sees.
  5. 5. Why keep presence out of the log?
    Solution Changes many times a second, worthless after the user leaves, bloats log and replay. Broadcast and discard.
  6. 6. 800 live editors; the owning server is overloaded.
    Solution Cap active editors, rest read-only; batch/coalesce for viewers; fan out through pub/sub or edge relays while one server still orders ops; batch edits 50–200 ms. Never let a second server accept edits.

Mini project

OT server + 3 clients + a CRDT replica, with property tests.

  1. Start from the code above; write each server op to an append-only log with its revision.
  2. Snapshots every 100 revisions; a new server = latest snapshot + log tail must equal a replay from rev 0.
  3. Op IDs; a repeated (client, opId) is a no-op; test a lost ack.
  4. WebSocket layer; broadcast cursor messages, don't log them.
  5. Range comments: store start/end, transform both; test they still cover their words.
  6. Multi-character insert/delete; property tests must still pass (where transform bugs hide).
  7. Per-user undo, tested with concurrent edits.
Done when thousands of random runs converge, a crashed server recovers the same document, a duplicate changes nothing, and comments stay on their words.

Justify:

  • OT + owner server vs sequence CRDT (text quality, offline, team skill, rich-text transform cost).
  • Doc → owning server mapping; moving ownership safely on failure.
  • Snapshot frequency; history retention.
  • Editors beyond the cap. Comment anchors surviving concurrent edits.
  • Permissions on a live connection, incl. revoking mid-session (Ch 19).
  • Offline merge vs "please reload". Which estimate to load-test first.

Interview

  1. 1. How do two people edit one doc without overwriting each other?
    Answer Apply locally at once, send ops to a server that orders them, and use OT (transform concurrent ops) or a sequence CRDT (unique char IDs) so all replicas converge.
  2. 2. OT vs CRDT?
    Answer OT + central server: small messages, proven for rich text, but transform rules are hard to write and verify. CRDT: converges without a central order (offline, P2P) but carries per-char metadata and needs GC. Choose by offline needs, document model, and team experience; keep a server for persistence, permissions, history.
  3. 3. What is a tombstone?
    Answer A marker left where a char was deleted, so other replicas' ops that reference it still work. Removed by GC once every replica has seen the delete.
  4. 4. Show your own typing instantly yet stay correct?
    Answer Apply optimistically, queue unacked ops; transform incoming remote ops against the queue (OT) or merge by ID (CRDT). The server's order is the truth; the client converges to it.
  5. 5. Scale to millions of docs and a few huge ones?
    Answer Shard by doc ID, one owner per active doc. Add servers and move ownership. Hot doc: cap editors, batch + coalesce, fan out to viewers via pub/sub. Log + snapshots in durable storage so any server can take over.
  6. 6. Server crashes mid-edit?
    Answer Ops are acked only after the durable log write. New server loads snapshot + replays log; clients reconnect and resend unacked ops (op IDs make retries safe).
  7. 7. Undo?
    Answer Only your own last op. OT: inverse op transformed past everything since. CRDT: new op targeting the same char IDs. Test with concurrent edits.
  8. 8. Why not log presence?
    Answer High-frequency, short-lived, worthless after the user leaves. Broadcast and discard; only content ops are persisted.

Checklist

  • apply edits locally first; reconcile with the server's order
  • pick OT, CRDT or property LWW on purpose, say why
  • one owner per document orders operations
  • log every accepted op durably before the ack; snapshot regularly
  • op IDs make retries harmless
  • presence stays out of the log
  • check permissions on the live connection
  • test convergence with random edits and random delivery
