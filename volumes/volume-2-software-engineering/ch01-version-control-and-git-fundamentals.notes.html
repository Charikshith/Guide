Ch 1 — Version Control & Git Fundamentals

Volume 2 — Software Engineering · Contents · Next → Chapter 2 — Professional Git Workflow

Concept

What is version control? Why Git? How does Git work inside?

In one sentence: version control = a database of every saved state of a project, so you can go back, compare, work in parallel, and know who changed what and why. Git stores each state as a full snapshot and links snapshots into a history.

Mental model — a photo album with labels

Commit = photo of the whole project. Each photo points to the one before. Branch = sticky label on one photo. HEAD = your finger on the label you work from. Moving a label is cheap; photos never change.

Layer 1 · The problem

No tool → report_final_v2 report_REAL_final. Breaks once work is shared.

WithoutWith version control
no safe undogo back to any saved state
"who broke it?" = a guessauthor + time + message on every change
two people overwrite each otherchanges merge; real clashes show as conflicts
trying an idea risks working codea branch to try it on the side
no record of whyhistory is the record
can't rebuild a releasea tag names the exact state

Matters beyond code: CI builds from commits, review reviews commits, incidents ask "which commit broke it?".

Layer 3 · Why Git?

  • Fast + local: commit, diff, log, branch need no network.
  • Cheap branching: a branch = a 41-byte file → branch per task.
  • Safe: objects named by a hash of their content → damage/tampering is detectable; commits never edited in place.
  • Distributed: every clone is a full backup; work offline.
  • Standard: GitHub/GitLab/Bitbucket, every CI. Built 2005 for the Linux kernel; scales huge.

Layer 4 · Snapshots, not differences

Old tools: base file + list of changes (deltas). Git: the whole tree per commit. Unchanged file → not copied; new commit points at the same stored object. (Packfiles use deltas later to save disk — storage detail, not the model.)

Layer 5 · The object database

Everything lives in hidden .git — a key-value store: key = SHA-1 (40 chars) of content, value = content.

ObjectHoldsAnalogy
blobbytes of one file (no name)file content
treelist of mode, type, hash, namea folder listing
commitone tree + parent(s) + author + messagelabelled photo
tag (annotated)name + message → one objectpermanent sticker
  • Same content → same hash → stored once. Change 1 byte → new hash. History can't be edited silently.
  • A commit's hash covers tree + parent + author + message → vouches for all history behind it.
  • SHA-256 is replacing SHA-1 (git init --object-format=sha256); model unchanged.
Exam tip!
commit → tree → blob. Name lives in the tree, not the blob.

Layer 6 · The three areas

AreaWhatMoved by
Working directoryfiles you edityour editor
Staging area (index)the next commit, being builtgit add
Repository (.git)all committed historygit commit
  • Staging lets one commit hold one idea (git add -p).
  • File states: untracked → modified → staged → committed.

Layer 7 · History is a graph

  • Each commit stores its parent; a merge commit has two. → DAG (arrows back in time, no loops).
  • Branch = file with one commit hash (.git/refs/heads/main). Commit → current branch label moves forward. New branch = write a new file.
  • HEAD usually holds ref: refs/heads/main ("I'm on main"). Raw hash instead = detached HEAD: new commits have no label and can be lost.
  • Tag = label that never moves.
  • Merge: one side just behind → label slides (fast-forward). Both moved → merge commit. Same lines changed → conflict, fix by hand.

Layer 8 · Remotes

  • Remote = another copy (origin = the one you cloned).
  • git fetch = download commits, move origin/main; never touches your work.
  • git pull = fetch + merge (or rebase). git push = send commits, move the remote's label.
  • Push refused if it would lose remote commits (not a fast-forward) — protects others' work.

Layer 9 · Under the hood

  • Packfiles: loose objects compressed, similar ones stored as deltas → long histories stay small.
  • Reachability + GC: object kept while a branch, tag or reflog entry reaches it; unreachable ones deleted after a grace period (git gc).
  • Reflog: local log of where HEAD/branches have been → the "I lost my commit" safety net (Ch 2).
  • .gitignore: files Git won't track. Never commit secrets — they stay in history even after deleting the file.

Example

bash 
git init demo && cd demo                  # creates the hidden .git folder
echo "hello" > hello.txt

git status -s                             # ?? hello.txt   (untracked)
git hash-object hello.txt                 # ce013625030ba8dba906f756967f9e9ca394464a
                                          # same content gives the same hash on any machine

git add hello.txt                         # staged
git commit -m "add hello"                 # committed

git log --oneline                         # one line per commit
git cat-file -t HEAD                      # commit
git cat-file -p HEAD                      # tree aaa96ced...  (+ author, message)
git cat-file -p 'HEAD^{tree}'             # 100644 blob ce013625...  hello.txt
git cat-file -p ce013625                  # hello

cat .git/HEAD                             # ref: refs/heads/main
cat .git/refs/heads/main                  # the hash of the latest commit

git switch -c feature                     # a new branch = one new 41-byte file
echo more >> hello.txt
git commit -am "more"
git log --oneline --graph --all           # see both labels and the history

git diff HEAD~1                           # what the last commit changed
git restore hello.txt                     # throw away unstaged edits to a file
text 
.git/
  HEAD            ← which branch you are on
  config          ← settings for this repo (remotes, user)
  index           ← the staging area
  objects/        ← blobs, trees, commits (the key-value store)
  refs/heads/     ← one file per branch
  refs/tags/      ← one file per tag

Exercises

  1. 1. Show that Git names content by its hash.
    Solution Make two files with identical text in different folders; git hash-object on both gives the same hash. Add one character to one: the hash changes completely. After git add on both, .git/objects holds one object for the shared content, not two.
  2. 2. Find the three objects behind your first commit.
    Solution git cat-file -p HEAD → the tree hash; git cat-file -p <tree> → blob hashes + file names; git cat-file -p <blob> → the file text. commit → tree → blob.
  3. 3. You commit on a detached HEAD, switch to main, and the commit seems lost. Get it back?
    Solution Git printed its short hash when you left, and git reflog lists it. git branch rescue <hash> puts a label on it. A commit with no branch, tag or reflog entry is only deleted after the garbage-collection grace period.
  4. 4. Why is git fetch safer than git pull?
    Solution fetch only downloads and moves origin/*; your branches and files stay put, so you can look first (git log main..origin/main). pull also merges/rebases at once, which can start a conflict at a bad moment.

Mini project

Build a tiny VCS: minigit (blobs, trees, commits, log).

  1. minigit init creates .minigit/objects + a HEAD file.
  2. hash_object(bytes) = SHA-1 of "blob <size>\0" + bytes; store zlib-compressed at objects/ab/cdef....
  3. write_tree(dir): blob per file, tree per folder; return the tree hash.
  4. commit(msg): store tree + parent + message; update the branch file.
  5. log: walk from HEAD back through parents; print hash + message.
  6. Check: copy your objects into a real .git/objects; git cat-file -p <hash> should read them.
Done when committing the same folder twice stores no new blobs, and changing one file stores exactly one new blob, one new tree per changed folder, and one commit.

Interview

  1. 1. What is version control and why use it?
    Answer A system recording every saved state so you can undo, compare, branch, merge parallel work, and trace who changed what and why. Replaces copying folders; makes releases, reviews and CI reproducible.
  2. 2. Why Git, and how is it different from SVN?
    Answer Git is distributed: each clone has the full history → local, fast, offline, every clone a backup. SVN is centralized: one server, most actions need it. Git also makes branching almost free and names objects by content hash for integrity.
  3. 3. What is a Git branch?
    Answer A movable pointer (a file with one commit hash) to a commit. Committing moves the current branch's pointer forward. Not a copy of the files.
  4. 4. Working directory vs staging area vs repository?
    Answer Your files, the prepared next commit, the stored history. git add moves changes 1 → 2; git commit moves 2 → 3.
  5. 5. What does a commit contain?
    Answer Pointer to a tree (full snapshot), parent hash(es), author, committer, timestamps, message. Its hash covers all of that, so it vouches for the whole history behind it.
