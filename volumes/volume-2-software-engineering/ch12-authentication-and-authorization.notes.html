Ch 12 — Authentication & Authorization

Volume 2 — Software Engineering · Contents · notes from the chapter + the video "7 Authentication Concepts Every Developer Should Know"

Concept

Who are you? → then what may you do?

In one sentence: authentication proves identity ("you are Priya"); authorization decides permission ("Priya may read this invoice"). Every protected request needs both — in that order.

Mental model — a hotel

Front desk checks your passport → authN. You get a key card that opens only your room + gym → authZ. Doors don't phone the desk; they just check the card (= a token). Lost card? Cancel it, or it expires. Partner hotel takes the same loyalty account → SSO.

Video's big point!
Most devs mix up methods, token formats and frameworks. Sort them first (box below).
Common mix-ups (fixed in the video)
  • JWT is an authentication method JWT = a token format
  • Bearer = JWT Bearer = a pattern ("whoever holds it gets in"); JWT is the usual token
  • OAuth2 = login OAuth2 = authorization framework
  • SSO is an auth method SSO = a user-experience pattern (uses SAML / OIDC underneath)

1 · What is authentication?

TermQuestionExample
Identificationwho do you claim to be?a username
Authentication (authN)can you prove it?password, code, passkey
Authorization (authZ)what may you do?"admins can delete"
  • Factors: know (password) · have (phone, key) · are (fingerprint). 2+ = MFA.
  • Passkeys (WebAuthn): key pair on device, private key never leaves → nothing to phish.
  • 401 = not authenticated (missing/bad credentials). 403 = known, but not allowed.
  • Passwords: store a slow salted hash — Argon2id (1st), scrypt, bcrypt. Never plain, never fast hash.

2 · Basic auth

Authorization: Basic base64(user:pass)

  • Sent on every request. First try → 401, then client retries with the header.
  • base64 = encoding, not encryption → readable by anyone. Only over TLS.
  • No expiry, no clean logout. OK for internal tools / client-id+secret to a token endpoint. Rare for users.

3 · Digest auth

  • Server sends a random nonce; client replies with a hash (MD5 in classic form) — password itself isn't sent.
  • Better than Basic on plain HTTP, but still outdated: MD5, server must hold password-equivalent data, no help vs fake server.
  • TLS + modern schemes replaced it. Know it for interviews / legacy only.

4 · API keys

  • A random string per client, sent as X-API-Key or in the auth header. Server looks it up (key hash + scopes in a DB).
  • Identifies an app/project, not a person. Random string — no info inside (unlike a JWT).
  • Leaks = anyone can use it; no built-in expiry. Missing key → 400/401, bad key → 401.
  • Show once · store only a hash · scopes · rotation (2 live keys) · prefix sk_live_ so scanners catch leaks · never in URLs or Git.

5 · Session-based auth

  1. Login with credentials. 2. Server stores a session, sends a session-ID cookie.
  2. Browser sends cookie each request → server looks it up → user data or 401.
  3. Logout = delete the session. Stateful: server must remember.
  • Store: memory (lost on restart) · Redis (fast, built-in expiry — the usual pick) · SQL DB · files (doesn't scale).
  • Cookie flags: HttpOnly (JS can't read → XSS), Secure (HTTPS), SameSite (CSRF). Rotate the ID at login; set timeouts.
  • Great for classic web apps; harder for APIs / distributed systems. Instant revocation is the upside.

6 · Bearer tokens & JWT

Bearer = Authorization: Bearer <token> — whoever bears it gets access. Opaque token = random string, server looks it up (stateful). JWT = signed JSON, self-contained (stateless).

header . payload . signature  (base64url)

  • Claims: iss issuer · sub user · aud audience · exp expiry · iat · nbf · jti; plus roles/permissions.
  • Signed, NOT encrypted → payload is readable. No secrets inside.
  • HS256 = shared secret (verifier can also forge). RS256/ES256 = private signs, public verifies; keys published at a JWKS URL.
  • Every request validate: signature · pinned algorithm (reject none) · exp · iss · aud.
  • Verify locally — no DB hit → scales, lighter server load.
  • Catch: can't revoke before exp → short-lived tokens (+ deny-list if needed).

Access + refresh tokens

  • Access: short (video: 15 min – 1 h; chapter: 5–15 min). Used on API calls.
  • Refresh: long (days–weeks). Sent only to the auth server to get a new access token.
  • Access expires → 401 → client uses refresh token → new access token → retry.
  • Rotate refresh tokens each use; an old one reappearing = theft → revoke the family. Store hashed server-side.
  • Browser storage: not localStorage (XSS) → HttpOnly cookie or memory.

7 · OAuth 2.0

Delegated authorization — "what can this app access on my behalf?" The access token proves the app is allowed; it does not tell the app who you are.

Roles: resource owner (user) · client (app) · authorization server (Google, Okta, Keycloak) · resource server (the API).

GrantUse for
Authorization Code + PKCEanything with a user: web, mobile, SPA — the default
Client Credentialsmachine-to-machine, no user
Device CodeTVs, CLIs with no browser
Refresh Tokenrenew an access token
Implicit, Passworddon't use (gone in OAuth 2.1)
  • Example: connect Google Drive to an app → consent screen → authorization code → app swaps code for access token → reads files.
  • PKCE: client sends hash of a secret (code_challenge), later proves it with the code_verifier → stolen code is useless.
  • Also: state (CSRF), exact-match redirect_uri, scopes (orders:read).

8 · OpenID Connect (OIDC)

  • Authentication on top of OAuth2. Add scope openid.
  • Flow: sign in → login + consent → code → app swaps it for access token + ID token.
  • ID token = a JWT for the app: iss, sub, aud, exp, nonce (+ email/name). App verifies it, then makes its own session.
  • Access token → API. ID token → client app. Never send an ID token to an API.
  • Discovery: /.well-known/openid-configuration. "Sign in with Google / GitHub / Microsoft" = this.
Rule of thumb
OAuth2 = may this app access that?
OIDC = who is this user?

9 · SSO & identity protocols

  • Log in once at the IdP, reach many apps (Google → Gmail, Drive, YouTube, Calendar). IdP keeps a global session + SSO cookie; each app just verifies it.
  • Gains: one place for passwords + MFA · fewer passwords · one switch for leavers · central audit.
  • Costs: IdP is a critical target · single logout is hard · apps still keep their own session · provisioning is separate (SCIM).

10 · Authorization

  • Check on the server, on every request, deny by default.
  • ACL (per-resource list) · RBAC (user → role → permissions) · ABAC (policy over attributes) · ReBAC (relationships, Zanzibar-style).
  • Scopes limit a token for an app; roles limit a user. Need both.
  • BOLA / IDOR: GET /orders/42 works for anyone logged in → always check this user may touch this object.
  • Keep policy in one layer (library / OPA / Cedar), least privilege, expire elevated access.

python 
# Verify a JWT correctly (PyJWT): pin the algorithm, check audience and issuer.
import jwt
from jwt import PyJWKClient

jwks = PyJWKClient("https://auth.example.com/.well-known/jwks.json")

def verify(token: str) -> dict:
    key = jwks.get_signing_key_from_jwt(token).key          # picks the key by "kid"
    return jwt.decode(
        token, key,
        algorithms=["RS256"],                                # never trust the token's own alg
        audience="orders-api",
        issuer="https://auth.example.com",
        options={"require": ["exp", "iss", "aud", "sub"]},
    )

def can_read_order(claims: dict, order) -> bool:
    return "orders:read" in claims.get("scope", "").split() and order.owner_id == claims["sub"]
    # scope allows the kind of action; the owner check stops BOLA/IDOR

Exercises

  1. 1. Decode a JWT by hand: what is and isn't protected?
    Solution Split on ., base64url-decode parts 1–2: every claim is readable. Part 3 is only the signature. Tamper-evident, not secret — never put passwords or personal data in the payload.
  2. 2. "We use JWTs, so logout just deletes the token in the browser." What's wrong?
    Solution A copied token stays valid until exp. Use short access tokens, revoke the refresh token on logout, and for instant cut-off keep a deny-list of jti (or a per-user "valid since" time).
  3. 3. Three checks besides the signature?
    Solution exp (small clock-skew allowance), iss is the issuer you trust, aud names this API. Also pin the algorithm, check scope, and check the user may access that object.
  4. 4. Pick a method: (a) staff dashboard, (b) public payments API, (c) nightly internal job.
    Solution (a) OIDC SSO with the company IdP (Code + PKCE) + MFA. (b) API keys with scopes, rotation, per-key rate limits — or OAuth2 Client Credentials. (c) Client Credentials with a short-lived token, or mTLS; secret in a secret manager.
  5. 5. Why isn't a plain OAuth2 access token proof of who logged in?
    Solution It's for the API, may be opaque, and says an app may do something — not who the user is. An OIDC ID token has aud = your client, sub and nonce. Using an access token as login proof allows token-substitution attacks.

Mini project

Login service: sessions first, then tokens with refresh rotation.

  1. Users with an Argon2id hash; rate-limit logins per account and per IP.
  2. Step 1: Redis session on login, cookie flags, CSRF protection, /logout.
  3. Step 2: RS256 access JWT (10 min) with iss, aud, sub, exp, scope + a JWKS endpoint.
  4. Refresh token: random, stored hashed with a family ID. /refresh returns a new pair; a reused old token revokes the family.
  5. GET /orders/{id} checks signature, aud, exp, scope and owner.
  6. Tests: tampered token, expired, wrong audience, alg: none, replayed refresh token, someone else's order ID.
Done when all six tests pass, logout ends a session at once, a replayed refresh token signs out the whole family, and another user's order returns 403/404.

Interview

  1. 1. Authentication vs authorization?
    Answer authN verifies who you are, authZ decides what you may do; authN first. Bad/missing identity → 401; known but not allowed → 403.
  2. 2. Sessions vs JWTs?
    Answer Sessions are stateful: instant revocation, but a lookup per request and a shared store. JWTs are self-contained and verified locally — good for APIs and microservices — but can't be revoked before expiry without extra state, so keep them short. One web app → sessions; APIs/many services → tokens.
  3. 3. OAuth2 vs OIDC?
    Answer OAuth2 delegates access (access token for an API). OIDC adds an ID token and a standard way to learn who the user is. OAuth2 alone isn't a login protocol.
  4. 4. Authorization Code + PKCE — and why PKCE?
    Answer Redirect with a code challenge → user logs in and consents → short-lived code back → app swaps code + verifier for tokens. PKCE binds the code to the client that started the flow, so a stolen code is useless. Required for public clients; recommended for all.
  5. 5. Revoke access when using JWTs?
    Answer Short access tokens, revoke the refresh token (and family) server-side, and for immediate effect check a deny-list of token IDs or a per-user "valid since" time.
  6. 6. Design SSO for ten internal apps.
    Answer One IdP (Keycloak/Okta/Entra) speaking OIDC; SAML only where needed. Each app is a registered client using Code + PKCE and validating ID tokens (iss, aud, nonce, exp). MFA at the IdP, SCIM for provisioning, each app enforces authorization from roles/groups.
  7. 7. BOLA/IDOR and prevention?
    Answer User changes an ID (/orders/42) and reads someone else's data because only "logged in" was checked. Check ownership/permission per object on every request, in a shared policy layer, with tests using two users.

Checklist

  • know authN from authZ, 401 from 403
  • hash passwords: Argon2id / bcrypt / scrypt + salt
  • credentials and tokens only over TLS
  • validate JWT signature, algorithm, exp, iss, aud — every time
  • short access tokens, rotate refresh tokens
  • Authorization Code + PKCE; never implicit / password grants
  • authorization on the server, per object, deny by default
